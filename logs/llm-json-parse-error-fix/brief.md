# brief: llm-json-parse-error-fix

## C01 の1行

TypeScript で LLM の出力を受け取る処理を書き始めた人が、LLM の返した JSON を `JSON.parse` に渡して `SyntaxError` が出たとき（エラーの文をそのまま検索したとき）に、原因の見分け方と直し方を答える記事。

## 検索意図のタイプ

エラー（Fix）。guides/01 §1 の表で、合う記事型はトラブル解決。

Google（日本）の上位10記事は見ていない。このセッションで使えた検索は WebSearch（米国向けの検索）だけで、2026-10-31 に「LLM JSON.parse エラー コードフェンス 途中で切れる」で検索した。返ったのは7件で、どれも英語のページ（Rust のライブラリ lc-core の json_parse の説明、PromptLayer の用語集「JSON parsing error」、GitHub の issue、MemberJunction の RepairJSONEscaping）だった。日本語の検索の上位とは別物なので、検索意図の判定の根拠にはしていない。

その7件から読み取れたこと（参考。記事の出典にはしていない）: どれもコードと処理の手順が中心で、原因にはコードフェンス、前後の説明文、途中で切れた応答、末尾のカンマが挙がっていた。GitHub の issue には、括弧の深さを数えて切り出すと文字列の中の括弧で範囲がずれる、という報告があった。この記事の `extractJson` は括弧を数えず、最初の `{` か `[` から最後の `}` か `]` までを切り出す。そのため JSON の文字列の中の括弧ではずれないが、前の説明の文に括弧があるとずれるので、その場合を本文に1文で書いた。

タイプは、タイトル（与えられたもの）が「落ちる原因と直し方」で、エラーの文を持った人が来る前提から、エラー（Fix）に決めた。

この記事の見出しとの対応:

| テンプレート | この記事 |
|---|---|
| リード | 冒頭3文（原因は2つ、前後の文字は切り出す、切れた出力は取り直す） |
| 結論（先に解決策） | H2「エラーの文の頭で原因と直し方が決まる」（エラーの文 → 原因 → 直し方の表） |
| 前提・環境 | H2「動かした環境と準備」（Node.js 22.22.0、依存なし） |
| 原因の説明 | H2「4つの見本で出る SyntaxError」（再現と、JSON のテキストが値1つだけでできている理由） |
| 原因別の解決策 1 | H2「Unexpected token は JSON の前後を切り出して直す」（変更前 `reproduce.ts` → 変更後 `fix.ts`） |
| 原因別の解決策 2 | H2「Unterminated string は stop_reason を見て取り直す」と H3「閉じ括弧を足すと、欠けたデータがそのまま通る」 |
| （根本の対策） | H2「Structured Outputs でも max_tokens の確認は外せない」 |
| それでもダメなとき | H2「それでも JSON.parse が失敗するとき」（ログに出す3つ、position の読み方） |
| まとめ（チェックリスト） | H2「確認すること」（4項目の箇条書き） |

型の決まりの守り方:

- エラーメッセージをタイトルと見出しに入れる。タイトルはワークフローが与えたもの（「JSON.parse で落ちる」「コードフェンス、途中で切れる」）。見出しに `Unexpected token`、`Unterminated string`、`SyntaxError` を入れた。`Unexpected token` の直後のバッククォートは、原稿の地の文に書くと ai-smell-lint のコードブロック除去（``` の対応づけ）が崩れるので、地の文と見出しには書かず、実行結果のコードブロックと表の説明で示した。
- 解決策を先に置き、原因の説明（RFC 8259 の JSON-text）は短くした。
- 変更前 → 変更後は、`reproduce.ts`（`JSON.parse`）と `fix.ts`（`parseLlmJson`）の2つの完全なファイルで対比した。断片の diff は、コピペで動かないので載せていない。
- 環境とバージョン（Node.js 22.22.0、エラーの文が Node.js のバージョンで変わること）を明記した。MDN の例のエラーの文は Node.js 22.22.0 で出た文と違う（出典1の例は `Unexpected token ] in JSON at position 13` の形）ので、記事のエラーの文は実行ログから写した。

## 書き手の態度（guides/03 不在1）

切れた JSON は直さない。閉じ括弧を足して読ませると、欠けたデータが正しいものとして通るので、`stop_reason` を見て取り直す。これを記事の主張にした（`run/05.log` で、閉じ括弧を足すと `JSON.parse` が成功し、`summary` が途中で止まったまま通ることを確かめた）。

## 読み終えた人ができるようになること

`JSON.parse` の `SyntaxError` の文の頭から、前後の文字の問題か出力が切れた問題かを見分け、前者は `extractJson` で切り出して読み、後者は `stop_reason` が `max_tokens` かを確かめて取り直す処理を書ける。
